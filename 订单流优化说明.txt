CoinPulse 订单流 Phase 1 优化说明
更新日期：2026-09-02

一、本次完成的优化内容

1. 新增本地订单流服务
   - 新增目录：orderflow/
   - 服务入口：orderflow/server.js
   - 使用 Node.js 连接 Binance Futures 的 aggTrade WebSocket。
   - 默认跟踪 BTCUSDT、ETHUSDT、SOLUSDT。
   - 本地 HTTP API 地址：http://127.0.0.1:8787
   - 接口：
     - /api/orderflow/status?symbol=BTCUSDT
     - /api/orderflow/1m?symbol=BTCUSDT&limit=120

2. 订单流 1 分钟聚合
   服务只保留聚合结果，不写入原始逐笔成交明细。每分钟记录：
   - 主动买入量 buy_volume
   - 主动卖出量 sell_volume
   - Delta（主动买量 - 主动卖量）
   - CVD（累计成交量差）
   - 成交笔数
   - 大单买/卖次数
   - 大单买/卖量

3. MySQL 持久化与磁盘控制
   - 新增表结构：orderflow/schema.sql
   - 表名：coinpulse.orderflow_1m
   - MySQL 数据目录已确认位于 D:/MySQL/MySQL Server 8.0/Data。
   - 默认仅保存 BTC、ETH、SOL 的 1 分钟聚合数据。
   - 默认保留 60 天；服务每 6 小时自动清理超过保留期的数据。
   - 配置文件 orderflow/config.json 已加入 .gitignore，不会提交数据库密码。

4. 前端订单流可视化
   - 保持既有自绘 Canvas K 线图和指标逻辑不变。
   - 新增“订单流 · Delta / CVD”独立面板。
   - 面板展示：
     - Delta 柱状图（绿色为主动买方占优，红色为主动卖方占优）
     - CVD 曲线
     - 最新 Delta、累计 CVD、主动买卖量、大单买卖量、成交笔数、数据时间
     - 本地服务、MySQL、Binance Futures 流的连接状态
   - 本地服务没有运行时，原有 K 线、指标、海龟策略仍然正常工作；订单流区域会清晰显示未连接，而不是误报中性数据。

5. 稳定性处理
   - Binance WebSocket 自动重连。
   - MySQL 不可用时，HTTP 服务和前端不会崩溃，并会反馈错误原因。
   - MySQL 恢复后服务会定时重试初始化。
   - 服务启动后会尝试读取已有聚合数据，用上次 CVD 作为重启后的累计基线。

三、这次优化带来的效果

1. 从“定时快照”升级为“持续订单流采集”
   原项目的聪明钱和微观信号主要依赖每 30 秒请求一次最近 1000 笔成交，样本会滚动覆盖，也不能形成连续的 CVD。
   新服务会持续接收 Futures aggTrade，并按分钟稳定聚合，因此可以看到方向性资金是否持续进入或流出。

2. 增加突破质量判断依据
   旧海龟策略判断依据主要是 K 线突破、ATR 和高周期 EMA。
   新增 Delta/CVD 后，可以检查：价格突破时主动成交是否同向；若价格上破但 Delta/CVD 走弱，后续可提示为低质量突破或观望。

3. 降低存储压力与隐私/安全风险
   不保存原始逐笔成交，避免高频数据快速占满磁盘。
   只保存少数币种、1 分钟聚合、60 天数据，适合当前 D 盘容量。
   本地网页只绑定 127.0.0.1，避免把 orderflow/config.json 的敏感配置通过局域网直接暴露。

4. 为回测和策略对比建立数据基础
   当积累足够分钟数据后，可以对比：
   - 纯海龟突破
   - 海龟突破 + CVD 同向
   - 海龟突破 + Delta 同向
   - 海龟突破 + 大单确认
   从而用真实数据检验过滤器是否改善胜率、盈亏比和最大回撤。

重要说明：订单流能提高“信号是否有成交支持”的可解释性，但不能保证提高收益。是否有效必须在足够长、覆盖不同市场环境的样本上回测验证。

四、后续优化方案

Phase 1.1：完成实时采集验收（优先）
目标：确认真实 Futures 数据能进服务、进图表、进 MySQL。
步骤：
1. 检查本机是否使用代理、VPN、公司网络或安全软件拦截 Binance WebSocket。
2. 观察 BTCUSDT 的 status 接口中 trades 是否开始增长。
3. 等待一分钟结束后，查询 orderflow_1m 是否有数据。
4. 在网页订单流面板确认 Delta 柱和 CVD 曲线显示。
5. 连续运行至少 24 小时，检查断线重连、数据空档和 MySQL 表增长量。

验收标准：
- connected=true 且 trades 持续增长。
- 每个已配置币种每分钟至多一条聚合记录。
- 重启服务后 CVD 能从最近存储值继续累计。
- 60 天清理任务不会影响当前分钟数据。

Phase 2：订单簿不平衡与大单增强
目标：增加近端流动性和主动大单推动判断。
实现：
1. 接入 Binance Futures depth 流。
2. 使用 REST snapshot + diff depth 维护本地订单簿。
3. 严格校验 lastUpdateId 和增量序号；检测断档时重新拉快照。
4. 计算前 1-5 档买卖量不平衡：
   imbalance = (bid_volume - ask_volume) / (bid_volume + ask_volume)
5. 把盘口不平衡按 1 分钟写入聚合表，不保存完整深度快照。
6. 大单阈值改为可配置的固定金额与滚动分位数结合，避免 BTC/ETH/SOL 使用同一绝对阈值失真。

Phase 3：订单流过滤器接入海龟信号
目标：保持海龟原规则不变，在突破之后增加可开关的确认层。

建议规则：
1. 海龟向上突破后：
   - 最近 N 分钟 Delta 为正；
   - CVD 斜率为正；
   - 主动买入比例达到阈值；
   - 近端订单簿偏买方；
   - 有同向大单推动。
2. 海龟向下突破使用反向条件。
3. 采用评分或分级，不建议第一版使用任何单一硬条件：
   - 强确认：正常放行
   - 弱确认：降低仓位或标记“谨慎”
   - 反向/数据不可用：观望，不自动否定原始海龟信号记录
4. 前端显示过滤原因，后台推送消息也显示“海龟原信号”和“订单流确认结果”。
5. 默认先只影响展示与推送，不直接影响实盘/模拟交易；回测证明有效后再开放“严格过滤”。

Phase 4：回测与效果评估
目标：量化验证订单流过滤是否真正改善策略。
步骤：
1. 给海龟每次突破记录订单流快照与过滤结果。
2. 新增“纯海龟 / 海龟 + 订单流”对比回测选项。
3. 统计：交易数、胜率、平均收益、盈亏比、最大回撤、持仓时长、手续费敏感度。
4. 分币种、分周期、分市场状态比较，避免只用牛市或单一币种得到错误结论。
5. 设定最小样本量后才调整默认阈值。

Phase 5：吸收与 Footprint（进阶）
目标：在不违反存储约束的前提下增加更深入的订单流判断。
实现建议：
1. 吸收：大量同向主动成交但价格推进有限，结合分钟高低价、Delta 和 CVD 识别。
2. Footprint：只保存每分钟按价格区间汇总的买卖量桶，并限制价格层级数量与保存期限。
3. 在性能稳定前，不增加逐笔历史回放，也不保存完整订单簿快照。
